# 고객 모듈(C-01~04) — 구현 전에 정해야 할 정책 (2026-11-26)

**상태:** 서버에 고객 모듈이 없다(고객 테이블·API 없음). 주문은 고객 없이 만들어진다. **DEC-12(고객 최소정보와 보유)가 "승인/법률 검토" 미승인**이고 개인정보(이름·전화번호)가 처음 서버에 저장되는 기능이라, 아래 결정 전에는 만들지 않았다.

## 진행 결정 (2026-11-26, 사용자 지시)
위 제안안 **#1~#10을 최소 수집 1차판의 정책으로 채택**하고 구현을 시작했다. 보존기간만 DEC-12 법률 검토 결과를 따른다(미승인 항목은 그대로 남는다).
구현 현황(2026-11-26): **서버 1차판 완료** — 고객 테이블·이력(추가 전용)·RLS(031), 등록+중복 후보, 수정+전·후 이력, 익명화(Owner만), 목록·검색(이름 부분 일치 + 번호 3자리 이상, 목록은 끝 4자리만), 상세, 변경 이력(Owner 전·후 값 / 직원 사실·시각만), HTTP 6개 경로·OpenAPI.
주문 연결(#4)도 완료: 032 연결 테이블(추가 전용, 현재 고객 = 최신 연결), `POST/GET /orders/{id}/customer`, 안내 대기열 항목의 `customer`(이름·번호 전체). 같은 고객 재연결은 기록 없음, 폐기·취소·종결 주문과 익명화된 고객은 422, 연결 해제 명령은 없다(다른 고객으로 바꾸기만).
읽기 감사(#3)도 완료: 고객 상세·변경 이력·주문의 현재 고객 조회가 성공하면 감사 로그에 `GET …` 행(누가·어느 고객/주문)이 남는다. 목록·안내 대기열 조회와 실패한 조회(403·404)는 남지 않는다(안내 대기열은 번호를 싣지만 업무 화면이라 제외 — 필요하면 `auditRead` 한 줄로 켠다). 목록은 `cursor`/`nextCursor` 페이지를 지원한다.
**남은 것:** 보존기간은 DEC-12 법률 검토 후 확정. 연결 해제 명령·주문 목록/상세 응답의 고객 필드는 만들지 않았다(필요해지면 추가).

## 이미 확정된 규칙(변경 불필요)
- 고객 등록·변경은 **감사 이벤트**로 기록한다(STBR).
- **전화번호를 정규화**하고, **공유 번호는 자동 병합하지 않는다**(같은 번호의 고객은 "중복 후보"로만 표시)(STBR, UC-03).
- 정상 흐름: 이름·연락 수단 입력 → 번호 정규화 → **동일 서점** 중복 후보 표시 → 기존 고객 선택 또는 신규 생성 → 주문 연결(UC-03).
- 고객 변경 이력(C-04)은 탭이고 **민감 필드는 권한으로 제한**한다(IA).
- 고객 공개 주문(DEC-01)은 P1이며 P0는 직원 접수만이다.

## 정해야 할 것 (제안안을 먼저 적었다)

| # | 결정 | 왜 필요한가 | 제안안 |
|---|---|---|---|
| 1 | **수집 항목** — 필수·선택 필드 | 개인정보 최소 수집(DEC-12는 "이름 또는 별칭 + 연락 가능한 전화번호 필수"를 *제안*만 했다) | 이름(또는 별칭) 필수, 전화번호 필수(전화로 연락하는 구조), 이메일·메모는 선택 없음(1차 제외) |
| 2 | **보존·삭제 기간과 삭제 방식** | DEC-12가 "법률 검토 후 확정". 주문·결제 원장은 추가 전용이라 고객을 지우면 원장이 깨진다 | 주문에는 고객 ID만 연결하고, 삭제 요청은 **익명화**(이름·전화 비식별화, ID·주문 이력 유지). 기간은 법률 검토 결과를 따른다 |
| 3 | **누가 보는가** — 직원에게 전화번호 전체를 보일지 | "접근 최소화"(DEC-12). 직원이 전화를 걸어 안내하려면 번호가 필요하다 | Owner·직원 모두 전체 조회(안내 업무에 필요), 목록 화면은 끝 4자리만, 상세·이력 조회는 감사 로그에 기록 |
| 4 | **주문과의 연결** — 고객이 필수인가 | 지금 주문은 고객 없이 만들 수 있고 안내 대상(전화·SMS)은 고객을 모른다 | 고객은 **선택**(기존 주문 호환). 안내 대상 화면에 연결된 고객의 이름·번호를 보여 준다 |
| 5 | **중복 후보 기준** | "공유 번호 자동 병합 금지"만 정해져 있다 | 같은 서점·같은 정규화 번호 → 후보 표시(병합 명령 없음). 이름이 같으면 더 강한 후보 |
| 6 | **번호 정규화 규칙** | 국내 휴대전화만? 국제번호? 지역번호 유선? | 국내 번호만: 숫자만 남기고 `010…`·지역번호 형식 검증, `+82` 접두는 `0`으로 변환 |
| 7 | **마케팅 수신 동의** | DEC-12 "마케팅 동의 분리" | 1차 범위에서 **저장하지 않는다**(안내는 주문 업무 안내만, 마케팅 발송 기능 없음) |
| 8 | **고객 정보 변경 이력** 보존 범위 | C-04 "변경 이력, 민감 필드 권한" | 변경 전·후 값을 추가 전용 이력에 저장하고 Owner만 전체 조회, 직원은 변경 사실과 시각만 |
| 9 | **고객 검색 방식** | 목록 검색(C-01) — 이름 부분 일치? 번호 끝자리? | 이름 부분 일치 + 번호 숫자열 부분 일치(3자리 이상), 최신 등록순 |
| 10 | **병합·삭제 같은 파괴적 작업의 허용 여부** | 공유 번호 자동 병합은 금지지만 수동 병합은 미정 | 1차는 수정만(병합·삭제 명령 없음), 익명화는 Owner만 |

## 결정되면 서버에서 만들 것
고객 테이블·이력(추가 전용)·RLS, `POST/GET /customers`·상세·수정·변경 이력, 번호 정규화·중복 후보, 주문·안내 대상과의 연결(선택), 감사 기록, 명세·시험(권한·검색·정규화·중복 후보·익명화). 개인정보 보존기간 결정 전에는 **저장 필드를 최소화한 1차판**(위 제안안)부터 만들 수 있다.
