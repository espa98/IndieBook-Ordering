# 08단계 결과 보고 — 고객 안내·인도·결제 사실 기록

작성 기준: 작업 트리 (`main`, 마지막 푸시 커밋 `dbe31c1` 위에 환급·결제 정정 변경 포함). 실제로 실행해 확인한 것과 그렇지 않은 것을 구분해 기록한다.
공통 안전규칙의 5개 항목 순서를 따른다: (1) 읽은 문서와 충돌·미결정 (2) 변경 파일 (3) 실행한 명령과 실제 결과 (4) 미실행·미구현 (5) 다음 단계 승인 게이트.

## 0. 요약

고객 안내(대상 생성 · 문구 복사/공유 · 외부 발송 시도 · 직원이 기록한 결과 · 재안내 · 확보량 변경 시 obsolete · 7일 미수령 경고), 수령(인도) 등록(결제 확인 · 취소 잠금 · 부분 인도 · 출처별 소진), 결제 사실 기록(거래 입력 · 증빙 확인 · 무효 · 중복 외부 거래 차단 · 과수납 환급 필요 업무 · 환급 확인 · 오기록 보정)을 **메모리 저장소 기준으로 TDD 구현**했다. 테스트 **914개가 통과**하고 `tsc` 오류는 없다. 07단계의 836개 대비 **+78개**다.

프롬프트가 요구한 테스트 중 **중복 안내, 부분 인도, 미확인 결제 인도 거부, 중복 외부 거래**는 충족했다. **발송 실패**는 `FAILED` 결과와 재안내로 검증했다(실제 발송 채널 호출은 없다). **동시 인도**는 순차 경쟁(남은 1권을 두 번 요청)으로만 검증했고 **격리 DB가 없어 BLOCKED**다. **권한 검사·HTTP 진입점·OpenAPI는 08 전체에 없어서, 이 함수들을 외부에 노출하면 안 된다.**

**이 시스템은 PG 승인·환불을 실행하지 않는다.** 결제·환급의 "확인"은 직원이 외부 증빙을 보았다는 수기 기록(`STAFF_MANUAL_EVIDENCE`)이며, 제공사가 검증했다는 표시(`providerVerified` 등)는 어떤 기록에도 없고 테스트로 고정했다.

### 1.3 제가 정한 값 (문서에 없음, 확인 필요)
- **결제 금액:** 원화 정수 **문자열**(`^[1-9]\d*$`), 합산은 `BigInt`. 수단은 `CARD`·`EASY_PAY`·`BANK_TRANSFER`만.
- **중복 외부 거래:** 같은 서점·수단·**공백 제거한 외부 참조번호**. 다른 주문에 붙이는 것도 불가.
- **결제 상태:** 저장하지 않고 확인·무효·환급·보정 기록에서 파생. `paymentSummary.confirmedKrw` = 확인된 거래 합계 − 확정 환급 − 보정(**순액**). 인도 가능 한도는 이 순액이다.
- **무효 vs 보정:** 확인 전 거래만 무효(ST-Y03), 확인된 거래의 오기록은 감액 보정(ST-Y04, 원거래 보존, 누적 보정+확정 환급 ≤ 거래액).
- **환급:** 필요액은 과수납분 스냅샷, 환급 확인은 **원 결제를 지정**하고 (업무 남은 필요액, 원 결제 거래액 − 기환급) 이내. 활성 업무는 주문당 1개(`REFUNDED` 전까지).
- **안내:** 전체 확보(`FULL`)가 기본, 부분 확보(`PARTIAL`)는 직원 명시 선택. 같은 확보 스냅샷의 안내 대상 중복 생성 불가.
- **오류 코드:** 대상 없음·타 테넌트는 구별 불가한 동일 `NOT_FOUND`(404), 한도·상태 위반은 `BUSINESS_INVARIANT`(422), 입력 오류는 `VALIDATION_ERROR`(400), 권한 없음은 `FORBIDDEN`(403), 같은 키 다른 본문은 `IDEMPOTENCY_CONFLICT`(409).

## 5. 검증 품질 (TDD 준수에 대한 정직한 기록)

### 5.1 TDD
- 새 동작은 실패하는 테스트(RED)를 먼저 확인한 뒤 구현했다.
- **RED 없이 통과한 테스트**(보호용·기존 동작 고정): 각 명령의 "같은 멱등 키에 다른 내용 → 충돌"(공통 `executeIdempotent`), 부분 인도 누적, 남은 1권 순차 경쟁, 위임 없는 기본 거부, `longUnreceivedWarnings`의 설정 기준일·실패 안내 제외·전량 수령 제외.
- **규칙 위반 기록:** "한 번에 하나의 테스트" 규칙을 어긴 곳: 안내 대상 검증+`NOT_FOUND` 두 건. (07단계의 3건에 이어 총 4건째)

### 5.2 기존 테스트·작성 중 테스트 변경 (공개)
- **통과 중이던 테스트의 단언을 바꾼 적은 없다.** 바꾼 것은 모두 장면(fixture)이다: 새 필수 의존성(`stockReservationDeliveries` 등 07의 것 외에 `paymentVoids`, `refundConfirmations`, `notificationResults` 등)이 생길 때마다 해당 장면에 저장소를 추가.
- **아직 통과한 적 없던 제 테스트를 고친 것:** 인도 테스트에서 "다른 주문 물량"이 결제 부족으로도 거부될 수 있는 허점(주문 A에도 확인 결제를 추가), 재안내 테스트 제목이 "성공"까지 말했으나 케이스가 없어 추가, 환급 테스트에 "원 결제별 상한"을 주장하지만 실제로는 검증하지 않던 부분과 자리표시 테스트를 지우고 상한이 실제로 걸리는 장면(`heavilyOverpaidScene`)으로 교체, 결제 보정 테스트의 제목에서 검증하지 않는 환급 주장을 제거하고 별도 테스트로 분리.
- **의미 변경:** `paymentSummary.confirmedKrw`가 환급·보정 반영 순액이 되도록 확장했다(기존 두 테스트는 환급·보정이 없는 입력이라 그대로 통과).

### 5.3 구조 변경
- `deliverStockReservation`·`deliverAllocation`을 `validate*`/`plan*`과 저장 본체로 분리해 `postFulfillment`가 여러 출처를 "모두 검증 후 함께 저장"하게 했다. `createNotificationTarget`에서 `buildNotificationTarget`을 분리했다(재안내 재사용). 모두 기존 테스트가 통과하는 상태에서 했다.

## 6. 알려진 한계·위험 (외부 노출 금지 사유)

1. **권한·인증 없음:** `actorRole`은 요청 값이다. Owner 전용 규칙(결제 정정·환급 확인)은 서버가 신원에서 역할을 도출하는 계층 없이는 위조 가능하다.
2. **원자성은 "검증 후 연속 저장"이다.** 수령 거래+출처 인도, 환급 확인 등은 실제 DB 트랜잭션이 아니다.
3. **동시성 미보장:** 결제 한도·인도 한도 검증과 저장 사이 경쟁은 막지 못한다(BLOCKED).
4. **취소 요청 모델 부재:** 인도 잠금(D27)과 환급 필요 업무의 "취소로 인한 환급"(ST-Y05의 취소 사유)을 만드는 명령이 없다. 환급 필요 업무는 **과수납 사유만** 연다.
5. **개인정보:** 안내 기록에 고객 연락처를 저장하지 않는다(DEC-12 법률 검토 전). 따라서 발송 대상 연락처는 시스템 밖에서 직원이 확인한다.
6. **미구현:** 안내 템플릿 렌더링(MSG-001~003), 대기 목록(MSG-007), 공식 알림톡/SMS API(MSG-008/009, P1), 수령 정정(ST-F02, FUL-004), 택배(ST-F03, P1), 환급 실패·UNKNOWN(ST-Y07), 결제 시도 P2(ST-Y08/Y09), 주문 종결 판정(DEC-10), 환급 실행 자체(없음이 정상).
