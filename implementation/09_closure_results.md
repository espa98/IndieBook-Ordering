### 1.3 제가 정한 값 (문서에 없음, 확인 필요)
- **종결 표현:** `Order.status`는 OpenAPI 계약(`DRAFT`·`CONFIRMED`) 때문에 늘리지 않고 선택 필드 `closedAt`과 `version+1`로 기록. 종결된 주문은 `assertOrderOpenForTransactions`가 결제·예약·인도·조달·취소 요청을 거부.
- **종결 분리:** Staff는 `requestOrderClosure`(주문 불변)만, `executeOrderClosure`는 `executedBy: "SYSTEM"`만 허용하고 같은 호출에서 `evaluateOrderClosure`를 재계산.
- **D27 잠금:** `REQUESTED`/`APPROVED` 요청의 수량. 거절·철회·STALE·적용이면 해제. 인도·신규 취소 요청의 한도 계산에 사용.
- **권한:** 취소 요청·철회 = Owner/Staff, 승인·거절·적용 = Owner. 환급 요청·철회 = Owner/Staff, 환급 승인·거절 = Owner. 재개는 `SYSTEM`.
- **오류 코드:** 대상 없음·타 테넌트는 구별 불가한 동일 `NOT_FOUND`, 한도·상태 위반 `BUSINESS_INVARIANT`, 입력 오류 `VALIDATION_ERROR`, 권한 없음 `FORBIDDEN`, version 불일치 `VERSION_CONFLICT`, 같은 키 다른 본문 `IDEMPOTENCY_CONFLICT`.

### 3.4 원자성에 대한 정직한 평가
모든 복합 명령(취소 적용, 환급 승인, 종결 실행, 재개)은 **검증을 먼저 끝낸 뒤 연속으로 저장**한다. 검증 실패 시 아무것도 남지 않음은 테스트로 확인했다. 그러나 **저장 도중 실패(예: 두 번째 저장소 쓰기 예외)가 났을 때 첫 번째 쓰기를 되돌리는 롤백은 구현·검증하지 못했다.** 취소 적용처럼 여러 하위 명령(예약 해제, 처분 대기, 주문 수정)을 순차 호출하는 경우 특히 그렇다. 실제 트랜잭션 경계(영속 계층)가 정해져야 닫힌다.

## 5. 검증 품질 (TDD 준수에 대한 정직한 기록)

### 5.1 TDD
- 새 동작은 실패하는 테스트(RED)를 먼저 확인한 뒤 구현했다.
- **RED 없이 통과한 테스트**(보호용·기존 동작 고정): 각 명령의 "같은 키 다른 본문 → 충돌", 거절·철회 시 D27 잠금 해제(상태 파생 덕분), 환급 승인 시 대상 변경 재검증(기존 `confirmRefund` 검증이 처리).
- **규칙 위반 기록:** "한 번에 하나의 테스트" 규칙을 이번 단계에서도 여러 번 어겼다 — 종결 요청의 검증+`NOT_FOUND`, 취소 요청의 한도+인도 제외, 취소 적용 가드 두 건, 취소 결정의 재결정·STALE, 환급 요청의 중복 방지+자격 검증. 모두 같은 이유로 RED이거나 이미 통과였다. (07·08단계와 합쳐 정확한 횟수는 세지 않았다.)

### 5.2 기존 테스트·작성 중 테스트 변경 (공개)
- **통과 중이던 테스트의 단언을 바꾼 적은 없다.** 바꾼 것은 모두 장면(fixture)이다: 새 필수 의존성(`paymentCorrections`, 취소 요청·결정 저장소 등) 때문에 해당 장면과 직접 조립한 deps에 저장소를 추가, D27 잠금 헬퍼(`orderCancelLocks.lock`)를 실제 취소 요청 생성으로 대체.
- **아직 통과한 적 없던 제 테스트를 고친 것:** 종결 요청 테스트 제목의 검증하지 않는 주장 제거, 재종결의 모호했던 단언을 정책대로 정확히 수정, 재개 테스트에서 뒤엉킨 한 건을 세 건으로 재작성(검증하지 않던 "조건 유지" 주장 포함), 환급·보정 테스트 제목의 과장 정리.

### 5.3 구조 변경
- 인도의 취소 잠금을 테스트용 연결점에서 실제 취소 요청 기록으로 교체했다. `assertOrderOpenForTransactions`로 네 곳의 상태 검사를 통합했다. 모두 기존 테스트가 통과하는 상태에서 했다.

## 6. 알려진 한계·위험 (외부 노출 금지 사유)

1. **권한·인증 없음:** `actorRole`·`executedBy`는 요청 값이다. `SYSTEM` 전용 명령(종결·재개)도 호출자가 값을 넣으므로 서버 진입점 없이는 우회 가능하다.
2. **원자적 롤백 미보장**(3.4).
3. **동시성 미보장:** version·한도 검증과 저장 사이 경쟁은 막지 못한다(BLOCKED).
4. **미구현:** 전량 취소 `CANCELLING`과 취소 주문 종결(ST-O06/O08, BR-O02), 수령 정정(ST-F02, FUL-004)과 출처별 복원, 공급처 발주 외부 의무(`BR-P05/P06`) 조정과 종결 차단, 취소 적용 시 조달 배정 해제, 가격 변경(DEC-08), 예외 종결(DEC-16), 환급 실패·UNKNOWN(ST-Y07), 승인 감사 로그 필드, 승인 대기 자동 만료(D27 미결정).
5. **재개의 범위:** 재개 근거는 결제 보정뿐이다. 보정이 종결 조건을 깨뜨리는 경우만 재개하며, 인도 정정·취소 철회 등 다른 역거래는 근거로 인정하지 않는다.

## 7. 다음 단계 승인 게이트

- 1.2의 4번(취소 적용 시 주문 수량을 제자리에서 줄이는 방식), 1.3의 `closedAt` 종결 표현을 이대로 둘지
- 전량 취소(ST-O06/O08)·수령 정정(ST-F02)·공급처 외부 의무를 10단계 전에 구현할지, 이후 별도 단계로 미룰지
- 변경분(재개, 이 보고서) 커밋·푸시 여부
