## 4. 후반부 설계 제안

### 4.1 수량 모델 (발주 품목 단위)
```
Qsend     = 발주 품목 수량 (전달 시점에 고정, 이후 원본 보존)
Qreduce   = 품절 확정 수량 + 수락된 취소 수량   (두 경로의 합은 Qsend를 넘을 수 없음: 이중 차감 금지)
Qvalid    = Qsend − Qreduce
Qreceived = 0  (입고는 07단계. 06에서는 0으로 두고 BR-P01의 기입고 침해 금지는 07에서 강제)
```
`Qreduce`에 **들어가지 않는 것**: 고객 취소, 품절 예상, 지연, 취소 요청(수락 전), 거절·미응답 수량.

### 4.2 회신(ST-P07): 추가 전용(append-only) 이벤트
- 회신 이벤트는 수정·삭제하지 않고 쌓는다(원본 보존). 품목별 현재 상태는 이벤트에서 **계산**한다.
- 이벤트 종류: `CONFIRM(수량, ETA?)`, `OUT_OF_STOCK(수량)`, `DELAY(수량, ETA)`. (결정 1: `CONFIRM`·`OUT_OF_STOCK`은 미응답 풀과 지연 풀에서 가져올 수 있다)
- 모든 회신은 **증빙(`evidence`), 실제 회신 시각(`repliedAt`, 업무 발생), 서버 기록 시각(`recordedAt`)**을 가진다.
- 허용 상태: `SENT`, `ACKNOWLEDGED`. 그 외는 422.
- 불변식: `확정 + 품절 + 지연 + 미응답 = Qsend`, 각 수량 ≥ 0.

### 4.3 취소 요청(ST-P08/P10): 요청과 회신 분리
- 요청: `{ 발주 품목, 요청 수량, 사유 }`. 요청만으로는 `Qvalid`가 변하지 않는다(PO-010).
- 회신은 요청을 **참조**하고 `수락량·거절량`을 담는다. `수락 + 거절 ≤ 요청량`, 남은 **미응답량은 계산**한다(TC-77).
- 요청 상태는 **계산값**: 미응답이 있으면 `REQUESTED`, 모두 응답했으면 수락만 `ACCEPTED`, 거절만 `REJECTED`, 섞이면 `PARTIALLY_ACCEPTED`.
- 같은 요청에 대한 **중복 회신 차단**(요청 참조 + 멱등키), 요청 수량의 합은 `Qvalid`를 넘을 수 없다.
- **전량 취소 확정(ST-P10)**: 모든 품목의 `Qvalid`가 0이 되고 수락 근거가 있을 때 발주를 `CANCELLED`로 바꾼다. 이때 S3의 연결 규칙에 따라 해당 배정은 재연결 가능해진다.

### 4.4 상태 전이 (발주)
| 전이 | 조건 |
|---|---|
| `SENT → ACKNOWLEDGED` | 증빙이 있는 **실제 회신**이 기록될 때. 회신이 없으면 자동으로 바뀌지 않음 |
| `SENT/ACKNOWLEDGED → CANCELLED` | 모든 품목 `Qvalid = 0` + 수락 근거 |
| `SENT/ACKNOWLEDGED → CLOSED` | **06에서 구현하지 않음**(정상 입고·후속 해결이 필요해 07 이후) |

## 5. 결정 사항 (2026-11-23 사용자 결정, 모두 제안 권장안)

문서가 정하지 않았거나 서로 다르게 읽히는 4곳을 사용자에게 확인했고 아래와 같이 **결정되었다.**

| # | 결정 | 내용 |
|---|---|---|
| 1 | **지연 수량의 전환: 허용** | 지연(`DELAY`)으로 분류한 수량은 나중에 `CONFIRM` 또는 `OUT_OF_STOCK`으로 분류할 수 있다. 이벤트는 추가 전용으로 쌓고 원본은 고치지 않는다. 확정·품절은 **미응답 풀과 지연 풀**에서 가져온다 |
| 2 | **`ACKNOWLEDGED` 조건: 증빙 있는 첫 회신** | 품목 일부만 응답해도 증빙이 있는 실제 회신이 기록되면 `SENT → ACKNOWLEDGED`. 회신이 없으면 자동으로 바뀌지 않는다 |
| 3 | **취소 수락 권한: Owner와 Staff 모두** | STBR ST-P08/P10의 `O/S`를 따른다. 공급처의 실제 회신을 받아 기록하는 사실 입력으로 본다. **DEC-09의 Owner 승인 절차는 09단계(승인 워크플로우)에서 다룬다** |
| 4 | **고객별 영향: 06에서는 품목 합계만** | 취소 수락·품절 확정은 발주 품목의 `Qvalid`만 줄인다. 합산된 발주 안에서 어느 고객 연결이 줄어드는지는 07단계(입고 배분)에서 정한다. 연결은 그대로 보존한다 |

이 결정으로 달라지는 설계:
- 4.2의 "미응답 풀에서만"을 **"미응답 풀과 지연 풀에서"**로 읽는다. 품목별 상태는 `미응답 / 지연 / 확정 / 품절` 4개 풀이고, 합계는 항상 `Qsend`다.
- `Qreduce = 품절 확정 수량 + 수락된 취소 수량`은 그대로이며, 두 경로의 합은 `Qsend`를 넘을 수 없다.
- **결정 3의 위험을 인정한다.** Staff도 외부 의무를 줄이는 기록을 할 수 있다. 모든 기록에 증빙과 기록자를 남기고(기록자는 인증 계층이 생긴 뒤), Owner 승인 정책이 확정되면 이 단계의 함수에 승인 조건을 추가해야 한다.
- **결정 4의 한계를 인정한다.** 06 구현에서는 "합산 발주를 줄였는데 고객 연결 수량의 합이 발주 수량보다 크다"는 상태가 **허용**된다. 이 불일치를 해소하는 규칙이 07에서 필요하다.

## 8. 위험

- **권한 우회**: 06 함수가 진입점 없이 노출되면 권한 검사 없이 발주·전달이 가능하다. 05의 `guarded` 패턴을 06에도 적용해야 한다.
- **동시성**: 메모리 구현은 순차 초과만 막는다. 같은 배정을 두 발주가 동시에 가져가는 경합은 DB 없이 검증할 수 없다.
- **고객별 영향 규칙 부재**(결정 4): 합산 발주를 줄일 때 고객 연결을 어떻게 조정할지 정하지 않으면 07단계(입고 배분)와 충돌한다.
