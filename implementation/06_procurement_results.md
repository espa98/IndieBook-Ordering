## 0. 요약

조달 배정, 발주 초안/`READY`, 파일 출력(CSV), 실제 전달 기록, 공급처 회신(확정·품절·지연), 공급처 취소 요청과 회신(수락·거절·미응답), 전량 취소 확정을 **메모리 저장소 기준으로 TDD 구현**했고 테스트 **588개가 통과**한다(`tsc` 오류 없음). 프롬프트가 요구한 테스트 중 **다중 주문 묶음, 부분 회신, 취소 미응답/거절, 다른 tenant, 중복 키는 충족**했다.

**충족하지 못한 것:** 동시 수량 경쟁 테스트와 "DB 트랜잭션으로 N:M 수량 상한 보장"은 격리 DB가 없어 **BLOCKED**다. "중복 재발주 위험을 예외 업무로 남김"은 중복을 **거절**하는 데까지만 했고 예외 업무 큐는 없다. **권한 검사·HTTP 진입점·OpenAPI는 06 전체에 없어서, 이 함수들을 외부에 노출하면 안 된다.**

### 1.4 제가 정한 값 (문서에 없음, 확인 필요)
**구조·도메인**
- **조달 배정 모델**: `주문 품목 → 공급처, 수량`, 상태 `ACTIVE`/`RELEASED`. 한 품목의 활성 배정 합계 ≤ 품목 수량. 배정 1건은 취소되지 않은 발주 1개에만 연결
- 발주 품목은 **같은 도서의 배정을 합산**하고 원 주문별 연결(`links`)을 유지. 발주 생성 입력은 `lines`가 아니라 **배정 ID 목록**(1.2의 8번)
- 회신은 **추가 전용 이벤트**이며 **기록된 순서대로** 적용(`repliedAt` 순서가 아님)
- 취소 요청 상태는 **저장하지 않고 응답에서 계산**. 미응답이 남으면 일부가 수락·거절돼도 `REQUESTED`
- `Qreduce = 품절 확정 + 수락된 취소`, 합은 `Qsend`를 넘을 수 없음. 수락된 취소는 확정·지연 풀을 **바꾸지 않는 별도 차감**
- 요청 가능 수량 = 현재 `Qvalid` − 아직 응답받지 못한 기존 요청의 미응답량
- **전량 품절만으로는 취소 확정할 수 없음**(수락된 취소 회신이 근거여야 함). 미응답 요청은 취소 후에도 `REQUESTED`로 남김
- 취소 회신은 **발주 상태를 바꾸지 않음**(BR-P02). 전이는 별도 확정 명령으로
**검증·오류**
- 오류 코드: 초안 주문·비활성 공급처·해제된 배정·다른 공급처의 배정·이미 연결·`READY`가 아닌 발주·수량 초과 등은 `BUSINESS_INVARIANT`(422), 없는 대상과 **타 테넌트 대상은 구별 불가한 동일 `NOT_FOUND`**(404). 상한 초과에 STBR 제안의 `ALLOCATION_LIMIT` 대신 API V2.2의 코드를 사용
- `eta`: `DELAY`는 필수, `CONFIRM`은 선택, **`OUT_OF_STOCK`은 거절**(입고 예정이 있으면 품절이 아니라 지연). 형식은 달력상 유효한 `YYYY-MM-DD`. 과거 `eta`는 검사하지 않음
- `deliveredAt`·`repliedAt`은 RFC3339 **UTC(`Z`)만**, 유효한 날짜, **미래 거절**, 밀리초 없는 입력은 정규화. 업무 발생 시각과 서버 기록 시각(`recordedAt`)을 분리
- 전달 방식 6종(`WEB EMAIL PHONE MESSENGER FILE API`), `fileVersion`은 선택이며 주면 이 발주의 **출력 이력에 실제로 있어야 함**
- 회신·전달·취소 회신은 **증빙(`evidence`) 필수**
**출력(CSV)**
- 열은 `bookId,quantity`만(공급처 파일에 고객·주문 정보 제외), CRLF, `DRAFT`/`READY`만 출력 가능, 출력은 **상태·버전을 바꾸지 않고** 이력(스냅샷·당시 발주 버전·발주별 파일 버전)만 남김
- **CSV 주입 방어**: `= + - @`, 탭, CR로 시작하는 값에 `'` 접두, RFC 4180 이스케이프

### 3.2 수량 모델 (`poLineState`, BR-P01)
발주 품목 수량은 항상 **미응답 / 지연 / 확정 / 품절** 4개 풀로 나뉘고 합은 `Qsend`다. `DELAY`는 미응답에서, `CONFIRM`·`OUT_OF_STOCK`은 미응답 또는 지연에서 가져오며 풀보다 많이 가져가면 거절한다. `Qreduce`는 품절 확정과 수락된 취소의 합이고 `Qsend`를 넘으면 거절한다(회신 쪽과 취소 회신 쪽이 **대칭**으로 확인).

### 5.2 기존 테스트 변경 (공개)
05단계 때 이미 있던 테스트 파일에서 06단계 전체에 **삭제·수정된 줄은 3개 파일의 4줄**(`git diff`로 확인)이며 모두 **`lineId` 추가에 따른 품목 기대값 변경**이다(`addOrderLine`, `createOrderService`, `getOrder`). 검증 내용은 그대로 두고 `lineId: expect.any(String)`만 추가했고 `toEqual`의 엄격함을 유지했다. 구현에 맞춰 기대를 약화한 것이 아니라 요구사항이 바뀐 경우다.

### 5.3 변이 실험
각 규칙을 망가뜨려 의도한 테스트만 실패하는지 확인했다. 변이 정의 수(재실행·무효 실행 제외): S0 2 · S2 6 · S3 12 · S4 10 · S5 20 · S6 35 · S7 19 = **104건**. 이와 별도로 **멱등 `payload` 필드 전수 스캔**을 했다.

**실험이 찾은 테스트 빈틈(모두 보강):**
| 발견 | 내용 |
|---|---|
| **멱등 본문의 체계적 약점** | 전수 스캔 **26건 중 20건 생존**. S2~S5와 05단계 주문 확정에서 "같은 키·다른 본문" 테스트가 필드 1~2개만 확인. 같은 키로 다른 요청이 오면 첫 결과를 조용히 반환할 수 있었음(예: 품절 확정 회신이 이전 확정 회신 결과로 응답). `payloadCoverage` 추가 후 재스캔 **30건 중 생존 0건** |
| 품목별 합계 상한 | 단일 품목 주문만 테스트해 품목 구분을 지워도 통과 |
| 취소 요청의 멱등 필드 | `reason`·`poLineId`가 멱등 비교에서 빠져도 통과 |
| 취소 회신의 누적·독립 | 누적 수락량, 요청 간 독립, 품목 간 독립을 못 잡음 |
| 음수 수량 테스트 | 합이 0이라 다른 검사(`합 ≥ 1`)가 대신 걸려 **엉뚱한 이유로 통과** |
| 전량 취소의 수락 근거·품목 구분 | 수락 근거 검사를 격리해 확인하지 못했고 다품목 시나리오가 없었음 |

**동치 변이 1건**: 취소 회신에서 "요청의 발주 소속 확인"을 지워도 바로 뒤 검사가 같은 `NOT_FOUND`를 내는 이중 방어라 테스트 빈틈이 아니어서 유지했다.

### 5.4 제 실수와 정정
1. **변이 실험 수치 오류**: S3 보고의 "18건"은 S2의 6건을 이중으로 센 값(실제 12건)이었고, 중간 보고서 초안의 "약 40건"은 근거 없는 추정이었다. 둘 다 정정했다.
2. **무효 변이 실험이 3번 발생**(유효한 결과처럼 보였으나 모두 실험 도구의 문제): (1) CSV 변이 4건이 정규식 이스케이프 오류로 **적용되지 않았는데 "통과"로 보임**, (2) 취소 회신의 변이 한 건이 문법 오류로 테스트 파일이 로드되지 않음(490개만 실행), (3) S7 연쇄 효과의 변이 스크립트에 인자 순서 버그로 소스 전체가 깨짐. 매번 결과가 이상해 보여 원인을 확인했고, 이후 **변이 적용 여부 검사**와 **전체 테스트 수 검사**로 무효를 걸러내는 방식으로 바꿔 재수행했다.
3. **테스트가 틀린 이유로 통과**: 음수 수량 케이스(위), 그리고 다른 품목의 회신이 섞여도 한도를 넘지 않는 수치를 써서 변이를 못 잡은 테스트 1건.
4. **편집 실수**: `poLineState.ts`를 `Edit`가 의도와 다르게 쪼개 놓아(불필요한 `finalize`) 읽어서 확인한 뒤 바르게 다시 썼다.
5. 테스트 헬퍼의 리터럴 타입 오류(테스트는 통과하는데 `tsc`는 실패)를 수정. `it.each` 제목 형식 오타 2회 수정.

## 7. 위험
- **권한 우회**: 진입점 없이 노출되면 권한 없이 발주·전달·취소가 가능하다.

- **07단계 충돌**: 고객별 영향 규칙(한계 5)이 정해지지 않으면 입고 배분과 발주 수량이 어긋날 수 있다.
- **문서 지연**: `05_orders_results.md`는 `lineId`·OpenAPI 스키마 분리·멱등 결함 수정을 아직 반영하지 않았다.
