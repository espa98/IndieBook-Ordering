# 05단계 — 주문 접수와 확정

## Bolt.new에 붙여넣을 프롬프트

당신은 BookFlow Ordering의 웹 프런트엔드 개발자다. 먼저 `00_공통_실행규칙.md`를 적용하고, 아래 파일을 실제로 읽어라.

참조 문서: Docs/03_UI_UX/Ordering_WebP0_Wireframe_UIUX_Guide_V1.1_비판적검토_개선본.md; Docs/05_API_Security/API_명세서_V2.2.md

## 이번 단계의 실행 지시
O-02/O-02-01, O-03, O-04, O-04-04/05를 구현한다. 신규 주문 2단 입력(고객→품목·수량·확정 가격), 초안/보류/확정 구분, 목록 필터·검색·페이지네이션, 주문 상세의 주문/조달/입고/배분/안내/인도/결제 독립 상태 및 타임라인을 구현한다. 초안 UUID와 확정 시 서점별 표시번호는 구분하며 번호를 브라우저에서 생성하지 않는다. CONFIRM_ORDER는 API 검증된 경우에만 활성화; idempotency key, expectedVersion, 충돌/중복 확인 UI 구현. 고객 공개 주문은 제외. 테스트: 0/음수 수량 차단, 복수 품목, 중복 확정 클릭, 버전 충돌, API 실패 후 결과 조회.

## 작업 방법
1. 현행 코드와 참조 문서의 화면 ID/필드/규칙/우선순위를 대조하고 구현 목록을 작성한다.
2. 기존 구현을 보존하면서 컴포넌트·라우트·폼·검증·오류 상태를 구현한다. 화면마다 로딩/빈 상태/오류/권한 없음/재시도 UI를 포함한다.
3. API가 실검증되지 않았으면 `DEMO MODE` 또는 비활성 기능으로 구분한다. 백엔드/DB를 임의 변경하지 않는다.
4. 가능한 테스트를 실행하고 실패한 항목은 수정하거나 근거와 함께 미완료로 보고한다.
5. 화면 ID별 변경 파일, 실제 API 연결 여부, 테스트 결과, 정책 게이트, 다음 단계 진행 조건을 한국어로 요약한 뒤 멈춘다.

## 완료 기준
- 문서에 정의된 P0 화면 동작과 오류 상태가 확인된다.
- 미승인 정책은 활성화되지 않는다.
- 테스트되지 않은 API를 성공 처리하지 않는다.
- 이전 화면/데이터의 회귀 오류가 없다.
