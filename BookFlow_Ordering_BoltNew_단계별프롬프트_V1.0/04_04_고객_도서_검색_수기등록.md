## 이번 단계의 실행 지시
C-01~04, B-01~05 화면을 구현한다. 고객은 구현된 API(`GET/POST /customers`, `GET /customers/{id}`, `…/updates`, `…/changes`, `…/anonymization`)에 연결한다. **최소 수집: 이름(또는 별칭)+국내 전화번호만**(이메일·메모·마케팅 동의 필드를 만들지 않는다). 목록은 번호 끝 4자리만, 상세는 전체이며 상세·이력 조회는 서버가 감사 기록을 남긴다. 변경 이력은 Owner에게만 전·후 값을, 직원에게는 변경 사실·시각만 보인다. 익명화는 Owner만(삭제 대신 익명화), 중복 후보는 등록 응답의 `duplicateCandidates`로 표시한다. 도서 검색은 `GET /book-search`로 YES24에 연결한다(실제 계약 확인됨): **ISBN 검색은 ISBN-13 13자리만**(ISBN-10은 400이므로 입력 단계에서 막는다), 제목과 저자는 서버에서 구분되지 않는 같은 검색이다(검색 유형 선택을 두더라도 결과가 같을 수 있음을 알린다). 결과에는 **"출처: YES24"를 표시하고 `detailUrl`로 YES24 상세 페이지를 연결**해야 한다(이용약관). 검색 결과를 모아 별도 저장하는 기능은 만들지 않는다. 503이면 수기 등록으로 안내한다. 주문 연결용 고객 선택은 `POST/GET /orders/{id}/customer`(선택 사항, 다른 고객으로 바꾸기만 가능). ISBN 없는 독립출판물 수기 등록 지원, 도서명·판매가 필수, 출처/조회 시각 표시, 주문 스냅샷 불변. 공유 전화번호 자동 병합 금지. 고객 정보 보존기간은 서점 설정(기본 15일, Owner가 변경)이며 **Owner가 직접 "보존기간 적용"을 실행할 때만** 익명화된다 — 화면이 자동으로 삭제·익명화하지 않는다. 테스트: ISBN 없음, API 장애, 동명이인/공유번호, 민감정보 노출.

## 작업 방법
1. 현행 코드와 참조 문서의 화면 ID/필드/규칙/우선순위를 대조하고 구현 목록을 작성한다.
2. 기존 구현을 보존하면서 컴포넌트·라우트·폼·검증·오류 상태를 구현한다. 화면마다 로딩/빈 상태/오류/권한 없음/재시도 UI를 포함한다.
3. API가 실검증되지 않았으면 `DEMO MODE` 또는 비활성 기능으로 구분한다. 백엔드/DB를 임의 변경하지 않는다.
4. 가능한 테스트를 실행하고 실패한 항목은 수정하거나 근거와 함께 미완료로 보고한다.
5. 화면 ID별 변경 파일, 실제 API 연결 여부, 테스트 결과, 정책 게이트, 다음 단계 진행 조건을 한국어로 요약한 뒤 멈춘다.

## 완료 기준
- 문서에 정의된 P0 화면 동작과 오류 상태가 확인된다.
- 미승인 정책은 활성화되지 않는다.
- 테스트되지 않은 API를 성공 처리하지 않는다.
- 이전 화면/데이터의 회귀 오류가 없다.
