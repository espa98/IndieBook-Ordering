# Ordering 기능별 요구사항 정의서 (FRD) V1.0

**기준:** Ordering PRD V1.1 — 비판적 검토 및 개선 통합본 (2026-11-20)

**문서 상태:** 상세설계 초안 / 제품 책임자 승인 전

**목적:** PRD의 기능 요구사항을 개발·테스트 가능한 단위로 재정의하고 기능별 입력, 처리, 출력, 검증, 권한, 예외, 인수 조건을 연결한다.

## 1. 문서 적용 원칙

- 이 문서의 요구사항 ID, 우선순위와 제품 범위는 PRD V1.1의 8장을 기준으로 한다.
- PRD에 없는 필드·UI·검증 방식은 **[설계 제안]**으로 구분하며 확정 요구로 취급하지 않는다.
- **P0**는 첫 MVP, **P1**은 초기 후속, **P2**는 확장이다. `P0 권장`, `P0/P1` 표기는 원문의 결정 유보를 그대로 유지한다.
- 고객 공개 주문(ORD-002)은 **P1 변경 제안**이다. 제품 책임자 승인 전 확정 범위로 보지 않는다.
- 외부 메시지 전송, PG 승인, 공급처 API/EDI는 1차 MVP에서 구현 완료를 전제하지 않는다.
- 수량·금액 변경은 원장·배분 이력 및 트랜잭션 정합성을 우선한다.

## 2. 공통 기능 명세

| 항목 | 공통 요구 |
|---|---|
| 테넌트 격리 | 모든 서점 소유 업무 데이터는 tenant_id로 범위를 제한하고 FK 연결에서도 동일 테넌트 여부 검증 |
| 인증/인가 | Supabase Auth + Membership 역할 + RLS + 서버 측 검증을 함께 적용 |
| 변경 이력 | 변경자, 변경 시각, 이전/이후 값, 사유(중요 변경)를 보존 |
| 시간 | 서버 저장 시각과 화면 표시 시간대를 일관되게 관리. Asia/Seoul은 설계 기본 제안 |
| 수량 | 0보다 큰 주문 수량, 중복 배분 방지, 입고·수령 초과 방지 |
| 금액 | 부동소수점 대신 정밀 숫자 타입, 주문 시점 가격 스냅샷 |
| 멱등성 | 주문 생성·입고·배분·결제 기록의 재요청 중복 실행 방지 |
| 내보내기 | CSV/XLSX 다운로드 권한 검증 및 개인정보 포함 여부 확인 |
| 장애 | 외부 API 실패 시 수기 입력·수동 안내 경로 제공 |

## 3. 기능별 상세 요구사항


### 3.1 인증·테넌트 (AUTH)

**업무 흐름:** 회원가입 → 테넌트 생성 → 소속/역할 확인 → 업무 접근.

**주요 예외:** 로그인 실패, 중복 생성, 직원 비활성화, 타 테넌트 접근.

**역할:** Owner/Staff (고객 공개 기능은 P1 도입 시 Customer, 플랫폼 관리는 Platform Admin)


#### AUTH-001 — 이메일 회원가입·로그인. 비인가 세션은 내부 API 접근 불가

- **우선순위:** P0 / **출처:** PRD V1.1 (기존/수정)
- **기능 목적:** 이메일 회원가입·로그인. 비인가 세션은 내부 API 접근 불가
- **입력:** 사용자 선택값·관련 업무 객체 ID·필수 수량/상태/사유 등 해당 기능의 데이터. 구체 필드명은 화면·DB 명세에서 확정.
- **처리 규칙:** 로그인 사용자와 소속 서점·역할을 검증하고, 해당 객체의 유효 상태 및 수량·중복·변경 가능 여부를 확인한 뒤 처리한다.
- **출력:** 저장/처리 결과, 변경된 상태 또는 이력, 업무 목록·상세 화면의 최신 결과.
- **예외 처리:** 권한 없음, 대상 없음, 테넌트 불일치, 중복 요청, 입력 오류, 동시 변경 충돌은 데이터 변경 없이 오류를 표시한다.
- **인수 기준:** 이메일 회원가입·로그인. 비인가 세션은 내부 API 접근 불가 또한 타 테넌트 접근 및 동일 요청 중복 처리가 차단되고 결과 이력이 확인되어야 한다.
- **검증 시나리오:** 정상 1건, 필수값 누락, 타 테넌트 요청, 중복 실행, 관련 상태/수량 경계값을 시험한다.

## 4. 업무 간 연계 규칙

### 4.1 주문 → 발주

- 고객 주문 품목과 공급처 발주 품목은 N:M이며 `Order Item Allocation`에 **배분 수량**을 기록한다.
- 매장 보유분, 신규 발주, 기타, 미정의 조달 경로를 구분한다.
- 발주서 파일 생성과 실제 공급처 전달은 서로 다른 이벤트다.
- 발주 전달 이후 고객 취소가 발생하더라도 공급처 발주를 자동 취소 완료로 변경하지 않는다.

### 4.2 발주 → 입고 → 고객별 확보

- 발주 품목은 여러 차수로 입고될 수 있다.
- `Receipt Allocation`으로 입고 품목의 실제 수량을 고객 주문 품목에 배분한다.
- 고객 안내 가능 수량은 **고객에게 실제 배분된 유효 입고 수량**을 기준으로 한다.
- 같은 입고 수량을 복수 주문에 중복 배분하지 않는다.
- 입고 정정은 원 거래를 참조하는 별도 이력으로 처리한다.

### 4.3 확보 → 안내 → 수령 → 결제

- 수동 안내 기록은 고객 수신·읽음 확인과 다르다.
- 수령 수량은 고객 주문 품목에 배분된 수량을 초과할 수 없다.
- 수령과 결제는 독립된 이력이다. 결제 기록은 카드 승인이나 회계 정산을 대체하지 않는다.
- 주문 완료 여부는 취소되지 않은 품목의 수령·미해결 예외·결제 정책을 종합하여 판단한다. **[설계 제안]** 완료의 정확한 후불 허용 규칙은 정책 승인 필요.
